# Архитектура и контракт платформы

[English translation](../en/ARCHITECTURE.md)

Общая платформа C++20 используется OS, Flare Preview и симулятором. Публичные OS API, Face SDK, Ignite и Companion имеют версию 1; совместимость дополнительно определяется ревизией разработки, сборкой и возможностями.

## Разделение ответственности

ESP-IDF управляет аппаратурой, native USB, аутентифицированным NimBLE, монтированием и восстановлением. Переносимый Core управляет транзакциями пакетов, согласиями, временем, выбором компонентов, событиями и жизненным циклом приложений. Runtime читает скомпилированный UI и отдельные ресурсы индексированным доступом. Заводские и пользовательские пакеты используют одинаковые манифест, валидатор и Runtime; заводские роли выбираются по метаданным, без встроенных раскладок циферблатов и переключателей по именам приложений.

Flare сохраняет QML-оболочку, тему, иконки, шрифты, эффекты и локализацию. PlatformClient отвечает за устройство и транспорт, IgniteHub — за пакеты и согласия, Studio — за компиляцию, Preview — за общий рендерер, CompanionService — за политику компьютера и метрики. Симулятор исполняет тот же Core через бинарные запросы во временном каталоге, без открытия устройства.

Реестры API и разрешений генерируются из `spec/services.json` и `spec/permissions.json`. Нереализованные службы возвращают `not_supported`; запись будущего разрешения не означает рабочую аппаратную интеграцию.

## Контейнер Ignite

Целые числа — little endian, кроме скомпилированных UI-сцен, чей кодек явно использует big endian. Нельзя приводить сетевые байты к нативным структурам C++.

Заголовок занимает 64 байта: `FLIGNIT\0` по смещению 0; u16 версии формата по 8; u16 размера заголовка по 10; u32 ревизии разработки по 12; u32 полной длины по 16; u32 числа записей по 20; u32 смещения индекса по 24; нулевой резерв u32 по 28; SHA-256 по 32. Хеш охватывает весь файл с обнулённым полем хеша.

Запись индекса — 24 байта: u32 ID, u16 типа секции, u16 кодека, u32 смещения, u32 длины, u32 флагов, u32 резерва. ID строго возрастают, секции не перекрываются, последняя заканчивается на EOF. Манифест ровно один. Типы: manifest=1, component=2, resource=3, UI=4, Lua=5, locale=6, signature=7. Кодек, флаги и резерв должны быть нулевыми. Лимиты: пакет 1 МиБ, 1024 секции, манифест 4096 байт; это пределы парсера и безопасности, а не слоты установки.

Манифест начинается с `FLM1`, затем строки UTF-8 ID/name/publisher с длиной u16, версия пакета u32, три бюджета памяти/инструкций u32, обязательные возможности u64, число разрешений u16 и пары строк permission/scope, число компонентов u16 и записи: строка ID, u16 типа, u8 роли, u32 ID секции. Максимум 64 разрешения и 32 компонента. ID не допускают обхода путей; неизвестные разрешения отклоняются.

UI поддерживает прямоугольники, скругления, линии, текст, небольшие маски и индексированные RGB565-изображения. Привязки текста используют только объявленные API. Доступ к своим ресурсам требует `ui.resources`. Шрифты — индексированные атласы FLGF с ограниченной временной памятью; изображения — FLIM, размеры и строки RGB565. TTF/PNG конвертируются на компьютере. Устройство не разбирает TTF, SVG, YAML и исходный JSON.

Описание сцен и алгоритмы растеризации/шрифтов сохранены как переносимые примитивы. Старые FaceRegistry, фиксированные раскладки, IgnitDefinition, менеджер трёх слотов, текстовый установщик и парсер команд удалены.

Кеш ресурсов содержит 32 дескриптора с циклическим вытеснением: заполнение кеша не ограничивает число доступных секций. FLIM читается только в пересечении изображения, экрана и `Canvas::clip`. Для FLGF отдельно читаются метрики и bitmap; кеш метрик ограничен 16 символами и очищается при смене привязки пакета. Runtime сохраняет вычисленные границы текста со шрифтами пакета в полях `Op::ink*` только в памяти. Эти поля не сериализуются; после декодирования сцены без вычисленных границ сохраняется консервативная перерисовка всего экрана.

Runtime разбирает `${...}` при запуске; незакрытая подстановка отклоняется как `invalid_package`, более 32 подстановок в одной операции — как `execution_limit`. Таблица концов подстановок занимает фиксированные 1024 байта; формирование текста использует ограниченные буферы без копирования `Values`. Lua-update сохраняет прежнюю частоту, но неизменившиеся свойства и опубликованные значения не требуют перерисовки. Core повторно использует привязки между изменениями времени, настроек, каталога и внешних данных. Каталог кеширует до 32 заводских ID на один обход; при большем числе используется полный поиск для сохранения защиты заводских идентичностей.

`PackageManager::revision()` инвалидирует кеши каталога после `begin()` и успешных commit/remove/rollback. Список для launcher ограничен прежним пределом строки; полный набор манифестов не удерживается. Идентичность для метрик кешируется на поколение Runtime и ревизию каталога и сверяется с загруженным пакетом; объявления, возможности, состояние приложения и актуальные grants проверяются при каждом обращении. Изменение файлов в обход PackageManager требует повторной инициализации через `begin()` и перезапуска затронутого приложения. SHA-256 по-прежнему не подтверждает издателя.

Wire-форматы, номинальные версии и ContractRevision не меняются. Изменились C++-размеры объектов (включая `Op`, `Runtime`, `Core`) и компаратор `Values` стал прозрачным (`std::less<>`); потребители должны пересобрать SDK и код, использующий его заголовки, вместе. При собственном подключении рендерера задайте `resourceMetrics` наряду с `resourceGlyph`, чтобы измерение текста не загружало bitmap. Новые кеши ограничены, но бюджет памяти и задержки на конкретной плате требуют отдельной проверки.

## Хранилище и восстановление

Заводские пакеты — read-only содержимое файловой системы образа прошивки. Пользовательские пакеты — неизменяемые объекты с именем по хешу контейнера; у каждого атомарная `.ref` и ссылка на предыдущую версию. Установка: `incoming.part`, устойчиво записанные блоки, хеш всего передаваемого файла, проверка контейнера/манифеста/UI, атомарная фиксация ссылки. Повтор блока разрешён только при совпадении байтов. Та же передача продолжается с устойчиво сохранённого смещения.

Прерванная установка не активируется. При старте повреждённая текущая ссылка заменяется валидной предыдущей; неудачное активное обновление откатывается. Пользователь не может заменить или удалить заводские идентичности. Неиспользуемые объекты и временные файлы прерванных атомарных записей очищаются; текущая передача сохраняется. Каталог обрабатывает один манифест за раз, не удерживая все неактивные в RAM.

Восстановление независимо от пользовательских пакетов. Flare может вернуть заводские роли; прошивка показывает собственный экран восстановления и обслуживает USB независимо от активного Ignite. Ключи доверия NVS и непустые повреждённые файловые системы автоматически не стираются.

## Безопасность

Разрешения A/P/S/U/X/R связаны с приложением, заявленным издателем, поколением установленного содержимого, точной областью, сроком, сессией или явным действием. Даже автоматический доступ требует декларации манифеста. Ограниченные права недоступны обычным пользовательским пакетам. Сессионное согласие заканчивается при отключении; обновления не наследуют расширенные или прежние согласия. Отзыв инвалидирует образцы и события в очереди.

CPU/RAM доступны лишь при действующем `companion.pc.metrics` с областью `cpu,ram` и независимо включённой политике Flare. Образцы без согласия устройства отклоняются, истекают через 10 секунд и очищаются при смене приложения. Сборщик метрик компьютера сейчас работает на Linux; неподдерживаемые сборщики не выдумывают значения.

SHA-256 проверяет целостность, но не подлинность издателя. Строка publisher не является подписью и не даёт привилегий. Доверие заводским пакетам основано на защищённом томе из прошивки. Пользовательские пакеты не имеют QProcess, произвольных команд оболочки, raw GPIO, памяти другого приложения или внутренних объектов транспорта.

BLE требует шифрования, аутентификации и привязки. Числовое сравнение подтверждается сохранённым локальным USB-каналом; BLE не открывает и не подтверждает собственное сопряжение. USB и BLE используют общий бинарный контракт без текстового резерва.

## Кадры Companion

Кадр: `FLCP`, u8 версии=1, u8 флага ответа, u16 ID метода, ненулевой u32 ID запроса, u32 длины полезной нагрузки, полезная нагрузка, CRC-32 заголовка и нагрузки. Максимум нагрузки — 4096 байт. Читатели принимают фрагменты, отклоняют ошибочную контрольную сумму, отбрасывают начальный шум. Ответ начинается с u16 кода Error. Явные общие Writer/Reader кодируют поля; строки имеют длину в байтах u16. ID служб закреплены в `spec/services.json` и сверяются с enum C++.

Рукопожатие передаёт протокол, ревизию разработки, build ID и необходимые возможности. Изменяющие состояние операции запрещены до проверок совместимости и доверия транспорту. Блоки передачи независимы от ATT-фрагментов. BLE использует подтверждаемые GATT-фрагменты по 20 байт и проверку поколения, чтобы отбрасывать работу отключённого соединения.

## Сборка и проверки

Команды из корня SDK приведены в [README](../../README.md). Тесты покрывают продолжение передачи, повторные блоки, нарушение целостности, обновление, откат, защиту заводских пакетов, разрешения и отзыв, пользовательские шрифты/изображения, устаревшие дескрипторы, многократные переключения и кадрирование. Автономный smoke-тест Flare загружает реальный QML и симулятор. Физические проверки в этот набор не входят.

Отступ — четыре пробела без табуляции; стиль в `.editorconfig` и `.clang-format`. Сгенерированные шрифты вручную не форматируются. Перегенерация: `tools/build_builtin_fonts.py --font-dir /path/to/lato`.

## Текущие ограничения

Lua 5.4.9 — единственный язык исполняемых приложений; ограниченный прототип работает в сборках компьютера, симуляторе и проверенной прошивке Spark. Фоновые службы не поддерживаются; будущие разрешения не означают реализованных API.

Проверенная плата имеет Flash 4 МиБ и PSRAM 2 МиБ. Прошивка задаёт два слота приложений, заводской том и writable storage. PSRAM необязательна: рендерер предпочитает её при наличии, строки DMA готовятся во внутренней памяти. Реальный запас памяти, проводка, BLE, сбои питания и автономность требуют аппаратной проверки. Успех тестов на компьютере не доказывает надёжность устройства или время работы от батареи.

Источники проектирования: [диалог](https://chatgpt.com/share/6aea633e-6744-83eb-8ef1-564b610456bb), [итог](https://chatgpt.com/share/6aeb20f7-8fbc-83ed-8fde-b505b0d2baf9). Текущая реализация только на Lua заменяет прежние предложения исполнения. [Самостоятельный SDK](SDK.md) описывает установку, `ignite init/build/check`, экспорт CMake `Flint::Platform` и подключение подмодулей. Валидатор использует этот Runtime и не удостоверяет аппаратную вместимость или подлинность издателя.

## Application API 1

Добавочное расширение Lua требует capability 128; бинарные форматы, идентификаторы протокола и ContractRevision не меняются. Runtime владеет очередью ввода (16), таймерами (8), ограниченными строковыми значениями и диагностикой. Core обслуживает разрешённые read-only службы и приватное хранилище пакета (16 ключей, 4096 байт, атомарная замена, CRC-32, одна успешная запись в секунду на Core). Все callbacks одного tick делят квоту инструкций; максимум 32 вызова служб. Адаптеры используют `postInput` и `nextWake`; аппаратная интеграция остаётся у потребителей. Изменились C++-размеры классов, поэтому потребителям нужна пересборка. Дополнительные фиксированные структуры и временная память хранилища не увеличивают Lua heap: прежнее вычитание 16 КиБ из декларации сохраняется, но полные native-пики/стек требуют повторных измерений на устройстве. Полный контракт и ограничения описаны в [SDK.md](SDK.md#application-api-1-ввод-состояние-и-службы). Симулятор исполняет те же Core/Runtime и проверяет сценарии на виртуальном времени.


## Companion Demand и диагностика

[Companion Demand v1](COMPANION.md) разделяет управление устройством и сессионного
поставщика данных внутри одного Core. Отключение постороннего клиента не сбрасывает
метрики и события локального runtime. Поколение потребителя меняется также при
suspend/resume; поколения input handles сохраняют прежний контракт.

Опциональный `Platform::microseconds` включает накопительные count/total/max для
обработки запросов, logic tick, scene, paint и resource reads. Чтения ресурсов,
ошибки и переполнения EventBus учитываются без новых задач и очередей. Фазы могут
быть вложенными. Диагностика сама не помечает сцену изменённой. Ответ ограничен
MaxPayload и 128 полями, Lua fault details имеют приоритет;
`diagnostics_truncated=1` сообщает о пропуске необязательных полей. Python-клиент
поддерживает числовые и текстовые значения. Изменились размеры C++-классов:
SDK и потребителей нужно пересобрать вместе; wire/package ContractRevision прежний.


## Продолжаемая проверка установки

Адаптеры используют `Core::process`, `tick`, `replyReady` и `takeReply` на одном
владельце. `install_commit` может не дать немедленного ответа; его прежний ответ
(тот же method/request ID и payload) выдаётся после проверки и публикации.
`Core::handle` остаётся синхронным интерфейсом для существующих нативных клиентов.
Форматы wire, пакетов и `incoming.part.meta` не меняются.

У Core один pending install и один слот результата. Верификация индекса/хешей
читает до 4096 байт за tick. Секции Lua/UI читаются порциями, за шаг декодируется
не более одной ограниченной сцены. Заголовок, манифест и проверка ссылок имеют
отдельные фиксированные пределы. Во время проверки работают локальный Runtime,
ввод и запросы других клиентов; изменения каталога и загрузка следующих блоков
отклоняются `invalid_state`. Смена активного приложения разрешена; необходимость
его перезапуска определяется при публикации.

Disconnect владельца до завершения отменяет проверку и закрывает файлы, сохраняя
staging и метаданные для resume. После атомарной публикации disconnect лишь
отбрасывает недоставленный ответ; совершённая установка не отменяется. После
reconnect клиент проверяет каталог. Отмена в Flare выполняется отключением
соединения. Клиент ожидает commit до 45 секунд и показывает завершение только
после успешного ответа.

`PreparedInstall` связывает проверку с открытым неизменяемым файлом и ревизией
PackageManager. Перед публикацией проверяются ревизия, исходная ссылка, версия
открытого файла и идентичность staging-объекта. Windows read handle запрещает
запись и допускает перенос в content-addressed storage; POSIX дополнительно
сравнивает inode/device. Хранилище принадлежит одному владельцу; внешние изменения
должны инвалидировать проверку. LittleFS не предоставляет полноценные host file IDs,
поэтому аппаратный адаптер и Core исключают параллельную запись staging.

Открытый проверенный файл передаётся Runtime без повторного полного SHA-256;
permissions не кешируются. Подготовка проверяет factory и прежний пакет также
продолжаемыми валидаторами. `Platform::require_factory=true` запрещает установку
при недоступном factory; firmware включает этот флаг, standalone simulator может
работать без factory. Повреждённый доступный factory не игнорируется.

Атомарные операции файловой системы, durable writes, сборка мусора метаданных и
редкие пути rollback/recovery пока синхронны. Порция данных не является строгой
wall-clock гарантией для медленного или неисправного носителя. Проверки под
нагрузкой на плате остаются необходимыми.

## Бюджет памяти и запуск

`Platform::memory` задаёт стабильную допустимость пакетов. Не передавайте сюда текущий свободный heap: временная нехватка памяти не должна скрывать установленный пакет или включать rollback. Опциональный `available_memory` проверяется только Runtime при запуске, отдельно для internal RAM и PSRAM; отказ возвращает `resource_exhausted`, сохраняя каталог и прежнее приложение до передачи владения. Обновление, прошедшее проверку целостности, не откатывается из-за временной нехватки памяти при активации; Core пробует заводские часы и сохраняет ошибку запуска.

Lua heap по-прежнему не превышает `declared internal - 16 KiB`. Дополнительно из декларации резервируется оценка native manifest/component allocations, `LuaApp::Impl` (включая опубликованные значения) и исходного Lua-текста на пике загрузки. При необходимости Lua heap уменьшается; минимум 16 KiB сохраняется. Это может отклонить запуск прежнего пакета, фактический native-пик которого не помещается в декларацию; формат и ContractRevision не меняются. Ошибка создания Impl возвращается явно, неудачный запуск закрывает файл и очищает ресурсы даже до lifecycle.create.

Диагностика разделяет `runtime_resident_bytes` (фиксированный Runtime, включая ResourceManager и его буферы, уже учтённый платформой при baseline), оценки native heap/пика и Lua used/peak. Оценки ёмкостей STL не включают allocator headers, фрагментацию, стек, validation/scene binding и аппаратные очереди. Полный пик и крупнейший свободный блок измеряются адаптером; оценки не являются обещанием общей RAM.

## Checkpoint времени и повторные проверки

`scene()` не пишет `epoch`. Владелец Core сохраняет его в `tick()` раз в 60 секунд; `nextWake()` учитывает срок checkpoint независимо от частоты кадров. Успешный `time_set` сохраняет время сразу и назначает следующий checkpoint через 60 секунд. После ошибки сохраняется работа часов в RAM, а диагностические `epoch_write_errors` и `epoch_checkpoint_disabled` показывают проблему. Автоматические повторы после ошибок ограничены тремя попытками (задержки 60, затем 120 секунд), затем возобновляются только после успешного `time_set` либо перезапуска. `epoch_durable_writes` считает успешные записи текущего Core.

При штатной работе сохранённое время отстаёт менее чем на один интервал checkpoint. После выключения длительность простоя неизвестна без RTC/новой синхронизации; после ошибок хранения этот интервал не гарантируется. Формат decimal epoch и остальные persistent formats не изменены, миграция не требуется.

По исходному коду ревизии 3275a64 commit читал кандидат полностью трижды: transfer SHA, Core inspect и PackageManager inspect. Теперь оба SHA считаются одним проходом тела, индекс дополнительно читается для проверки структуры; тест большого пакета проверяет точное число прочитанных байт. Подготовленная установка передаёт тот же открытый файл Runtime. Обычный `Core::launch` и `package_read` используют call-scoped `locate(..., File&, Package&)`, сохраняя результат проверки открытого файла до передачи/чтения без повторного SHA. Файл проверяется на изменение перед передачей Runtime. Кеш каталога и permissions не вводится; следующий вызов вновь проверяет объект. Поиск factory и fallback через role activation пока могут повторно проверять другие пакеты; глобального кеша нет.

Для файловых систем, запрещающих rename открытого файла, адаптер задаёт `Platform::rename_open_files=false`. PackageManager проверяет staging и ревизию, закрывает оба read handle, выполняет rename, затем открывает перемещённый объект и проверяет size/content mtime перед публикацией ref. Эта операция требует исключительного владения файловой системой и выполняется целиком на владельце Core; внешние writers запрещены. `ctime` может изменяться при rename и не сравнивается после него. Package продолжает ссылаться на тот же File; повторного SHA нет. При ошибке rename/reopen текущая ref не публикуется, recovery сохраняет прежний пакет. ESP LittleFS включает этот режим, Windows/POSIX по умолчанию сохраняют открытый handle. Host async-install tests проходят оба семейства путей через отдельные Core/PackageManager fixtures.
