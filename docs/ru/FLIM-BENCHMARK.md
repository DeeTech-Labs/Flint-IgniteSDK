# Проверки и стоимость FLIM v2 — 12 ноября 2026

[Спецификация](FLIM.md) · [English](../en/FLIM-BENCHMARK.md)

Измерения host: Windows, AMD Ryzen 7 5700X, MinGW GCC 15.1, Debug, по 200 итераций, тёплый файловый кэш. Источник — реальные подготовленные FLIM48×48; FILE открыт без stdio-буферизации. Проверка включает чтение заголовка/палитры/всех строк, draw — заголовка/палитры и всего изображения с alpha blending. Открытие FILE, сканирование каталога, SHA-256 пакета, передачу SPI эти времена не включают. Это средние конкретного прогона, не предел задержки и не измерение ESP32-S3.

## RAM: расчёт и границы

С точными флагами текущей ESP-IDF сборки (Xtensa GCC 15.2, picolibc) компилятор дал `sizeof(FlimDecoder)=36`, `sizeof(IconCache)=1088`, `sizeof(ResourceManager)=6136`, `sizeof(Scene)=1360`. Это проверенные размеры типов целевой ABI, не измерения heap платы. На Windows x64 decoder/cache — 56/1184 байт.

Строка960 и палитра768 байт используют существующий4096-байтный scratch глифов. Дополнительных пиксельных массивов нет. К decoder/cache добавляются16 байт icon IDs на Manifest и8 байт revision на Scene; сумма добавленных полей основного Core 1148 байт до возможного padding, то есть около1.1 KiB. Временные/дополнительные Runtime тоже получают decoder metadata и поля manifest/scene, но не отдельный image scratch.

Для шести тёплых файловых записей дополнительно учитывать до3072 байт LittleFS cache (настроено512/файл), объекты FILE/VFS/LittleFS, пути и allocator metadata. Базовая сумма состояния и файловых кэшей — около4.1 KiB **до** остального filesystem metadata. Это оценка, а не полный измеренный peak. Кэш не растёт с числом приложений.

Холодный miss использует существующую проверку каталога: потоковый SHA-256 и validation manifest/UI/Lua. Поэтому возможны временные существующие буферы manifest до4096 и Lua секции до16384 байт, а также строки/векторы манифеста; они не являются decoded image cache. Полный peak требует измерения с максимальными manifest и пакетами на плате. Размер FLIM сам по себе не определяет эту пиковую память. Без Lua/Runtime именно открываемого приложения и без загрузки всего пакета в RAM иконка доступна через Package/View.

## Проверено

- SDK MinGW: 20/20, включая 120 приложений, максимальные ID, длинные UTF-8 названия, focus/activation и partial redraw.
- SDK без Lua: 10/10; Lua factory проекты явно отвергаются как not_supported, Lua UI сценарии в этой конфигурации не регистрируются.
- Flare MinGW: 24/24, включая embedded Studio compiler с иконками, Preview, offline smoke и SDK suite.
- ESP-IDF6.1 ESP32-S3: build успешен; совмещённая прошивка751856 байта (около28% свободно в OTA1 MiB). Это размер общей рабочей версии, включая параллельные изменения UI/touch, не дельта одной поддержки FLIM.
- Сгенерированный factory содержит9 пакетов, сумма payload файлов28463 байта; LittleFS image196608. `littlefs list` подтвердил отсутствие staging-файла в образе: image собирается из `OS/build/factory`, а не исходного каталога SDK.

Optional CairoSVG/Cairo не установлен в окружении проверки: позитивный SVG backend-тест отмечен skip, отказ внешних SVG-ссылок проверен. Встроенный растровый конвертер и все native декодеры проверены. Удалённый Preview с доступом только к foreground-пакету показывает стандартную иконку для CatalogIcon; OS и локальный Core/simulator читают реальные иконки приложений.

На ESP32-S3 не измерялись скорость загрузки/рисования, heap high-water mark, качество дисплея и энергопотребление. Холодное открытие большого пакета/каталога остаётся отдельной стоимостью Flash I/O; результаты host decoder benchmark нельзя считать временем первого показа launcher.

Воспроизведение из SDK: `python tools/benchmark_icons.py build/icons-mingw/flim_tests.exe build/icons-mingw/icon-bench`. Спецификация и команды конвертера — в FLIM.md. Коммиты и submodule pins не обновлялись; потребители проверялись с явно заданным `FLINT_PLATFORM_DIR` на рабочий SDK.

После финального исправления повторно пройдены OS host5/5 и tooling9/9 уже в новой структуре каталогов. Инвалидация учитывает режим темы даже при одинаковых цветах; отказ валидного ресурса запрашивает следующий полный redraw. Тест изменения открытого файла выполняется на POSIX; Windows запрещает такую fault injection через FILE sharing policy, поэтому эта ветвь локально не исполнялась.
