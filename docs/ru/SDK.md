# Самостоятельный Flint IgniteSDK

Сборщик контейнеров отклоняет пакеты больше 1 МиБ (включая заголовок и индекс) и манифесты больше 4096 байт. Генератор реестра служб проверяет уникальность имён и ID, диапазон ID 1..65535 и булев тип `mutates` до записи заголовков.

Репозиторий: [DeeTech-Labs/Flint-IgniteSDK](https://github.com/DeeTech-Labs/Flint-IgniteSDK).

## Сборка и установка

Нужны CMake, компиляторы C/C++20, Python 3.11+ и Pillow в выбранном CMake interpreter до configure, включая штатную генерацию factory assets. Lua 5.4.9 включена с исходной лицензией и проверенным хешем архива; при сборке интерпретатор не скачивается. Команды из корня SDK:

```sh
cmake -S . -B build/docs-sdk -DCMAKE_BUILD_TYPE=Debug
cmake --build build/docs-sdk --config Debug --parallel 2
ctest --test-dir build/docs-sdk -C Debug --output-on-failure
cmake --install build/docs-sdk --config Debug --prefix build/docs-installed
build/docs-installed/bin/ignite init build/my-clock --id demo.clock --publisher demo
build/docs-installed/bin/ignite build build/my-clock/project.json build/my-clock.ignit
build/docs-installed/bin/ignite check build/my-clock.ignit
```

На Windows установленный скрипт `ignite` запускается через Python. В исходном дереве передайте `--validator build/docs-sdk/ignite-check` в `tools/ignite.py build/check`. Отчёты и диагностика CLI — UTF-8 независимо от кодовой страницы консоли. Ошибочная сборка сохраняет последний успешный пакет. JSON-отчёт показывает объявленные бюджеты и совместимость Runtime, но не измеренную вместимость устройства, подлинность издателя, допуск в магазин или автономность.

## Приложение Lua

`components[].logic: {"language":"lua","path":"main.lua"}` задаёт отдельную текстовую Lua section выбранного component. `budget`, `permissions`, `capabilities`, `app_api`, `sensor_api`, `ipc_api` также находятся внутри component; package union не даёт runtime неявных прав. UI app/watchface и не более одной службы могут иметь разные исходники и отдельные VM. Каждая Lua VM имеет 48..144 КиБ component budget, 1..100000 инструкций и исходник до 16 КиБ; service admission дополнительно ограничен model quantum/pool. FLM3 и точная ревизия `0x20261114` требуют пересборки всех packages/consumers. Envelope/API/Companion остаются версии 1. См. [фоновые службы и миграцию](BACKGROUND-SERVICES.md).

Исходник возвращает таблицу с `update(dt_ms, pressed)`. Для foreground первый вызов при загрузке имеет нулевое время, последующие выполняются Runtime или планировщиком Core. Core ограничивает шаг 100 мс. Ввод требует `input.focused`.

- `ignite.set(node, property, integer)` меняет x/y/w/h поддерживаемых собственных узлов UI. Нумерация с единицы; полноэкранный фон неизменяем. Границы соответствуют кодеку сцены. Ссылки на ресурсы и исполняемые обработчики заменять нельзя.
- `ignite.value(key, integer)` публикует до 16 значений для `${app.key}` в тексте. Ключи: 1..32 строчные ASCII-буквы, цифры и подчёркивания; значения — знаковые i32.

VM использует учитывающий память аллокатор и hook инструкций. Стандартные библиотеки, файловая система, OS, debug, загрузка модулей, корутины, динамическая загрузка и protected-call helpers не предоставляются. Ошибка уничтожает состояние; Core возвращается к часам/восстановлению. Это экспериментальная песочница, а не полный аудит безопасности. Счётчик инструкций не равен реальному времени. Нативные выделения памяти, разбор исходников, C-стек и задержки GC требуют измерений на устройстве.

```sh
build/docs-installed/bin/ignite build examples/flappy-bird/project.json build/game.ignit
build/docs-installed/bin/ignite run build/game.ignit --frames 120 --press-every 24 --image build/game.ppm
```

`run` — детерминированная симуляция без окна с искусственными нажатиями и итоговым PPM, а не интерактивная игра. Симулятор Flare использует тот же Core для обновлений по времени. Физический игровой ввод на этом этапе не подключён.

Сборки компьютера включают Lua по умолчанию; `-DFLINT_ENABLE_LUA=OFF` проверяет отклонение Lua-пакетов. Spark включает те же исходники/лимиты через `CONFIG_FLINT_LUA_RUNTIME`. Вложенные вызовы C ограничены 40; основной стек прошивки — 32 КиБ. Заголовки моста C++ включают `<climits>` для сохранения целочисленного ABI C/C++ ESP-IDF.

На Spark физически проверены анимация, повторное переключение приложений, ограничения исполнения/памяти и восстановление заводских часов. Сырые отчёты устройства хранятся вне репозитория; в PR указываются краткие результаты. Изменения движка, лимитов или нативных привязок требуют повторной проверки на устройстве.

Аутентифицированный метод Companion 21 (`diagnostics`) возвращает строки с целыми значениями: текущая/пиковая память VM, последняя ошибка логики и аппаратные поля памяти, стека, времени. Максимальные задержки накапливаются с загрузки и включают переходы/восстановление; это не устойчивый FPS и не чистое время интерпретатора. `tools/companion.py` — отдельный USB-клиент разработчика с pyserial, недоступный приложениям.

## Единый источник и закреплённые потребители

OS и Flare подключают SDK как `platform/` на неизменяемом коммите. Копирования, экспорта и синхронизации исходников нет.

```sh
git clone --recurse-submodules <consumer-repository>
git submodule update --init --recursive
```

Общие изменения вносятся, проверяются и публикуются в SDK, затем ссылка подмодуля обновляется в каждом потребителе и проверяется вместе с адаптерами. Не следуйте автоматически движущейся ветке. Одинаковые исходники устраняют расхождение реализаций, но не отменяют проверки контракта, сборки и возможностей.

Потребители на компьютере используют `add_subdirectory(platform)` и `Flint::Platform` либо установленный SDK с `find_package(FlintPlatform 1.0 EXACT CONFIG REQUIRED)`. ESP-IDF компилирует те же исходники через адаптер компонента, а не библиотеку компьютера. Конфигурация платы, транспорт и дисплей остаются в OS; Qt UI — во Flare. Заводские пакеты и примеры относятся к этой общей версии контракта.

## Дальнейшая работа

Для других плат и нативных привязок повторно измеряйте ресурсы, задержки и восстановление. Квоты инструкций не задают временную границу C-кода, парсера, GC и файлового восстановления. Приватное хранилище, доставка ввода и ограниченные службы реализованы в Application API 1 ниже; аппаратные адаптеры ввода/питания, стили и редактор Studio требуют отдельной интеграции. Подписи и публикация в маркетплейсе также остаются отдельной работой.

[Лицензии и дополнительные разрешения](LICENSING.md): разработка платных независимых Ignite разрешена; коммерческое встраивание Runtime — отдельный сценарий.

## Application API 1: ввод, состояние и службы

`"app_api": 1` внутри Lua component добавляет обязательный capability `128` (`CapAppApi`) к объявленным возможностям. Для Lua по-прежнему нужен бит `64`; например, `capabilities: 65` с `app_api: 1` компилируется в `193`. Старый Runtime отклонит такой пакет по отсутствующей возможности. Текущая ревизия `0x20261114` требует FLM3/FLIM v2 и пересборки всех пакетов и потребителей. Обратной совместимости нет; см. [иконки и FLIM](FLIM.md). ABI C++ расширенных классов не сохраняется.

Все новые вызовы доступны только пакетам с `CapAppApi`. Неверные количество/типы аргументов, диапазоны и некорректный UTF-8 завершают обработчик с диагностикой. Ошибки доступа/служб возвращаются как числовые значения `flint::Error`: `0` — успех, `4` — `not_supported`, `5` — `permission_denied`, `7` — `source_unavailable`, `9` — `quota_exceeded`. Полный список находится в `include/flint/contracts.h`. Это не исключения Lua; стандартные библиотеки и unrestricted `require`, `debug`, `io`, `os` не добавляются.

### События и жизненный цикл

Таблица приложения по-прежнему обязана иметь `update(dt_ms, pressed)`. Дополнительный необязательный обработчик `event(kind, value)` получает `press`, `release`, `hold`, `rotate`, `focus_lost`, `focus_gained`, `timer`, `suspend`, `resume`. `value` — знаковое i32, у таймера — ID 1..8, у suspend/resume — 0. Core доставляет события синхронно в своём цикле. Обработчика destroy нет; критичное состояние следует сохранять заранее. События не выполняются в фоне.

Адаптер OS передаёт `Core::postInput({kind, value, runtime.generation()})`. Нужны активное Lua-приложение и декларация `input.focused` с пустым scope. Очередь вмещает 16 событий; переполнение возвращает `quota_exceeded`, неверная генерация — `stale_handle`. При потере фокуса последующий ввод отбрасывается до `focus_gained`; уже поставленные события старого запуска не переходят в новый. Очередь очищается при suspend/stop. Для старых пакетов нажатие доставляется через `update(0, true)`. Физические кнопки, debounce и преобразование энкодера реализует адаптер OS, QML-представление — Flare.

### Планирование и таймеры

- `ignite.schedule(interval_ms)` возвращает код ошибки. Значения 1..86400000 задают интервал обновления; 0 отключает периодические update. Начальный `update(0, false)` всё равно выполняется. По умолчанию интервал 33 мс; dt в планировщике ограничен 100 мс.
- `ignite.timer(id, delay_ms, repeating)` возвращает код ошибки. Восемь слотов ID 1..8, задержка 1..86400000 мс, третий аргумент — boolean. Повторный вызов заменяет слот; delay=0 отменяет его. Срабатывание: `event('timer', id)`.
- Оба API требуют `time.timer.create` с пустым scope. Таймеры привязаны к запуску. При suspend они не доставляются, при resume отменяются; приложению доступно событие resume для повторной постановки. При stop/restart таймеры уничтожаются. Пропущенные периоды объединяются в одно срабатывание за tick, без догоняющего цикла.

`Core::nextWake()` возвращает абсолютный monotonic deadline в миллисекундах, включая ввод, таймеры, обновления, изменение минуты и истечение метрик. `UINT64_MAX` означает отсутствие срока. Адаптер должен вызывать `tick()` к этому сроку и пробуждать цикл при внешних событиях. На один Runtime tick все callbacks делят объявленную квоту Lua-инструкций; очередь и количество таймеров также ограничены. На обработчик/Runtime tick допускается до 32 вызовов служб, далее возвращается `quota_exceeded`. Это не гарантия реального времени: C-вызовы, файловые операции, parser и GC требуют аппаратных измерений.

### Службы и приватное состояние

`ignite.read(service [, key])` возвращает `value, error`; при ошибке value=nil. Поддерживаются только:

- `time.read` — Unix seconds; без установленного времени `source_unavailable`.
- `time.monotonic` — monotonic milliseconds.
- `system.info` — key `profile` (также по умолчанию) или `build_id`.
- `system.power.status` — key передаётся read-only адаптеру `Platform::power`; без адаптера `not_supported`. Доступные поля определяет профиль устройства; SDK не подставляет измерения.
- `system.locale.read`, `system.theme.read`, `system.settings.read` — строка по ключу активной локали, темы или системных настроек; отсутствующий ключ — `source_unavailable`.

Каждой службе нужна одноимённая декларация разрешения с пустым scope. Runtime проверяет capability, активное состояние/инициализацию и канонический класс разрешения перед вызовом Core. Перечисленные read-службы проверяются по component declaration; narrow outputs дополнительно используют текущую Core authorization, включая session `ui.brightness`. Регистрация произвольного permission не открывает новый API. Неизвестные имена возвращают `not_supported`. Регистрация разрешения не означает реализации службы. Никакие переданные приложением principals или grants не принимаются.

- `ignite.storage_get(key)` возвращает `string, error` или `nil, error`.
- `ignite.storage_get(key, default_integer)` возвращает сохранённое число i32; при отсутствии ключа или реализации — default с соответствующим кодом ошибки. Некорректное числовое содержимое возвращает nil/`invalid_argument`, повреждение файла не маскируется значением по умолчанию.
- `ignite.storage_set(key, string_or_integer)` и `ignite.storage_delete(key)` возвращают код ошибки. Целые ограничены i32; строки хранятся как UTF-8, числа — как десятичный текст.

Нужно `storage.private` с пустым scope. Ключ: 1..32 символа `[a-z0-9_]`, строка: до 192 байт без NUL. На пакет максимум 16 ключей и файл до 4096 байт. Пространство имён выбирает Core из манифеста активного пакета. Файл `app-<package-id>.kv` содержит версию, package ID, заявленного издателя, пары значений и CRC-32; заявленный издатель и CRC не доказывают подлинность. Обновление заменяет файл через существующий `writeAtomic`; неуспешная запись сохраняет предыдущий файл. Лимит успешных записей — одна в секунду на экземпляр Core, включая переключения приложений; перезапуск процесса сбрасывает лимит. Приложению следует объединять изменения и обрабатывать `quota_exceeded`. Данные сохраняются при обновлении/rollback того же ID/издателя, удаляются при uninstall. Миграции собственной схемы выполняет приложение. Это не encrypted/secure storage, backup или общий файловый доступ. Устойчивость к физическому отключению питания зависит от файлового адаптера и здесь не проверена.

### UI и диагностика

`ignite.value(key, value)` дополнительно принимает UTF-8 строки до 192 байт. Всего максимум 16 опубликованных ключей; общие лимиты текста/сцены сохраняются. `${app.key}` использует только значения приложения. Строки не интерпретируются повторно как шаблоны.

`ignite.set(node, property, integer)` дополнительно поддерживает `color` (RGB565, 0..65535), `visible` (0/1) и `image` для узла изображения. Фоновый первый узел остаётся неизменяемым. `image` возвращает код ошибки и принимает только ID FLIM-ресурса собственного пакета с проверкой `ui.resources`, заголовка, размеров и длины; размеры узла обновляются по изображению. Другие успешные set не возвращают значений. Узлам исходного JSON можно задать уникальный `id` из 1..32 символов `[a-z][a-z0-9_]*`. Компилятор создаёт локальную таблицу `ui`, например `ignite.set(ui.indicator, 'visible', 0)`. Имена входят в текст Lua и его лимит 16 КиБ; формат сцены не расширяется, порядок/нумерация её узлов сохраняются.

`ignite.log(text)` принимает UTF-8 до 128 байт, возвращает код ошибки. На запуск хранятся первые 8 записей, далее `quota_exceeded`; stdout и файлового доступа у приложения нет. `Runtime::diagnostic()` сохраняет ошибку, этап load/update/event, сообщение Lua со строкой, память used/peak, израсходованные инструкции и журнал после уничтожения VM. Ограниченный отчёт последнего сбоя сохраняется в Core при восстановлении и доступен через аутентифицированный Companion diagnostics. Сообщение ограничено 160 байтами, журнал — 8×128; лог не содержит native pointers или debug-доступа.

### Воспроизводимые сценарии

```sh
python3 tools/ignite.py build examples/counter/project.json build/counter.ignit --validator build/docs-sdk/ignite-check
python3 tools/ignite.py run build/counter.ignit --scenario examples/counter/scenario.json --runner build/docs-sdk/ignite-run --image build/counter.ppm
```

`run` использует общий Core и виртуальные monotonic часы. JSON содержит ровно `steps` (1..4096 шагов, файл до 256 КиБ). Операции: `advance` с `ms` 0..86400000; `input` с kind и необязательными value/expect (ожидаемый код ошибки постановки); `suspend`, `resume`, `restart` (новый запуск приложения), `reboot` (новый Core на том же хранилище); `expect_text`, `expect_state`, `expect_error` (последний код ошибки Core); `permission` с permission/scope/enabled через доверенный Companion API. Отзыв поддерживается для уже реализованных grant-разрешений; automatic-разрешения этим механизмом не отзываются. Неизвестные поля/операции и неверные типы отклоняются. Первая неуспешная проверка завершает CLI с ненулевым кодом и номером шага. `--storage` сохраняет состояние между запусками CLI, `--factory` задаёт заводские пакеты для сценариев восстановления. Без них используется временное хранилище. Драйверы дисплея/ввода и физические BLE, Flash, RAM, стек, задержки и батарея сценарием не проверяются.

## Бюджет памяти и запуск

`Platform::memory` задаёт стабильную допустимость пакетов. Не передавайте сюда текущий свободный heap: временная нехватка памяти не должна скрывать установленный пакет или включать rollback. Опциональный `available_memory` проверяется только Runtime при запуске, отдельно для internal RAM и PSRAM; отказ возвращает `resource_exhausted`, сохраняя каталог и прежнее приложение до передачи владения. Обновление, прошедшее проверку целостности, не откатывается из-за временной нехватки памяти при активации; Core пробует заводские часы и сохраняет ошибку запуска.

Foreground Lua heap не превышает `declared internal - 16 KiB`. Дополнительно из декларации резервируется оценка native manifest/component allocations, `LuaApp::Impl` (включая опубликованные значения) и исходного Lua-текста на пике загрузки. При необходимости Lua heap уменьшается; минимум 16 KiB сохраняется. Это может отклонить запуск прежнего пакета, фактический native-пик которого не помещается в декларацию; формат и ContractRevision не меняются. Ошибка создания Impl возвращается явно, неудачный запуск закрывает файл и очищает ресурсы даже до lifecycle.create.

Диагностика разделяет `runtime_resident_bytes` (фиксированный Runtime, включая ResourceManager и его буферы, уже учтённый платформой при baseline), оценки native heap/пика и Lua used/peak. Оценки ёмкостей STL не включают allocator headers, фрагментацию, стек, validation/scene binding и аппаратные очереди. Полный пик и крупнейший свободный блок измеряются адаптером; оценки не являются обещанием общей RAM.

## Touch и интерактивные системные экраны

Touch-пакеты указывают `app_api: 1` и capabilities `CapTouchEvents=2048`, `CapInteractiveUi=4096` вместе с Lua/Declarative/AppApi (итого 6337). Эти флаги описывают поддержку API Runtime, а не наличие физического сенсора на устройстве. Ввод требует `input.focused`, навигация — `ui.navigation`, каталог — `packages.list`.

`InputEvent` сохраняет прежние первые поля `kind/value/generation` и добавляет `x/y` (логические координаты), `pointer` (0..15) и `at` (monotonic ms). Новые виды: `touch_down`, `touch_move`, `touch_up`, `touch_cancel`. Координаты ограничены −320..640 для доставки движений за пределами viewport. Устаревшая generation отвергается. Соседние move одного pointer объединяются, down/up/cancel не заменяются. `event(kind, value, x, y, pointer, at)` передаёт координаты без создания Lua-таблицы на каждый отсчёт; старые обработчики игнорируют дополнительные аргументы. Адаптер использует часы Core и будит владельца цикла после постановки ввода. Аппаратного touch-драйвера эти изменения не добавляют.

- `ignite.read('packages.list', 'count')` возвращает число доступных плиток и код ошибки. `revision` позволяет проверить изменение каталога.
- `ignite.catalog(index)` возвращает `name, target, error`; index начинается с 0. Target — проверенная строка `package/component`, имя укорочено по метрикам сетки. Список совпадает с индексами иконок каталога.
- `ignite.action('role', 'clock'|'launcher'|'settings')` и `ignite.action('launch', target)` возвращают код ошибки и ставят переход после Lua callback. Нужен фактический focused release/up; вызов из load/update/timer возвращает `user_interaction_required`. Generation связывает отложенное действие с текущим запуском.
- `ignite.action('system', command)` дополнительно требует заводской пакет с активной ролью Settings. Команды: `ble_toggle`, `offset_up`, `offset_down`, `language`, `motion`. Обычный пакет не получает эти права, даже объявив роль Settings.

Общие обработчики жестов подключаются на компьютере через `components[].logic.includes`: до восьми относительных UTF-8 Lua-файлов внутри корня проекта, последовательно перед основным `components[].logic.path`. Итоговый исходник вместе с автоматически созданными UI IDs ограничен прежними 16 КиБ. Runtime не выполняет `require` и не получает доступ к файловой системе. Объявленный бюджет базовых Lua-экранов — 48 КиБ internal и 4096 instructions; лимиты платформы не увеличены.

`reduce_motion` — сохранённая настройка `0/1`, доступная стандартным `settings_get/settings_set`. Она отключает автоматическую инерцию и вступительное движение, сохраняя прямое отслеживание пальца. Передача событий из Flare Preview и физического контроллера требует соответствующего адаптера; host-тесты SDK подают их непосредственно через Core.

## Иконки приложений

Формат FLIM v2, поля проекта/manifest, тематические варианты, команды конвертера и ограничения памяти описаны в [FLIM.md](FLIM.md). Исполняемый пример: `examples/icons/project.json`. `ignite.catalog(index)` возвращает `name, target, error`; placeholder symbol удалён. Для узла `catalog_icon` доступно `ignite.set(node, "catalog", index)`.

Штатные иконки Clock и Settings имеют авторские цветные INDEX8 и отдельные A4-маски. Исходные PNG находятся в `system/assets/`; геометрию можно воспроизвести командой `python tools/build_system_icons.py` в `build/generated/system-icons/`, затем после review перенести PNG в `system/assets/` и собрать пакеты через `python tools/build_system.py`. Эти команды выполняются на компьютере с Pillow, не в прошивке. Числовой read-only ключ `utc_offset_minutes` у `system.settings.read` предоставляет типизированное значение UTC; исходный строковый `utc_offset` сохранён.

## Генерация без изменения исходников

Pillow нужен для штатной генерации factory-пакетов при CMake configure, включая сборки без тестов.

CMake автоматически запускает `cmake/FlintGenerate.cmake`. Результаты находятся в `<build>/generated/include/flint/`, `<build>/generated/factory/` и `<build>/generated/examples/<name>/sample.ignit`. Библиотека использует сгенерированные заголовки перед исходными, установка SDK экспортирует именно их. Тесты получают пути через `FLINT_FACTORY_DIR` и `FLINT_EXAMPLES_DIR` и не зависят от сохранённых бинарных пакетов в исходниках.

Прямой вызов `generate_registry.py` по умолчанию пишет в `build/generated/include`, `build_system.py` — в `build/generated/factory` и `build/generated/examples`. Независимые сборки должны задавать собственные каталоги:

```sh
python3 -B tools/generate_registry.py --output build/generated/include
python3 -B tools/build_system.py --output build/generated/factory --examples-output build/generated/examples
# Firmware: compile only factory packages.
python3 -B tools/build_system.py --output build/firmware-factory --skip-examples
```

Повторная генерация не переписывает неизменившиеся файлы. Каждый изменённый файл публикуется атомарной заменой; ошибка компиляции входного проекта оставляет предыдущие пакеты нетронутыми. Набор пакетов целиком не является атомарной транзакцией: потребитель должен дождаться успешного завершения генератора. Каталоги вывода должны принадлежать одной сборке; не направляйте их на исходные `factory/`, `examples/` или `include/`.

`build_system_icons.py --output <dir>` и `build_builtin_fonts.py --font-dir <fonts> --output <dir>` также пишут в `build/generated/` по умолчанию. Обновление сопровождаемых PNG/шрифтов — отдельный ручной перенос и review результатов, а не побочный эффект сборки. Сохранённые исходные factory/sample-пакеты и заголовки остаются снимками для прежних потребителей; новая CMake-сборка не обновляет их и не использует их вместо актуальной генерации.

Текущие touch/UI-контракты имеют `ContractRevision=0x20261114`, при номинальном Application API 1. Подключайте соответствующее дерево SDK целиком: заголовки, `core_ui.cpp`, `core_touch.cpp`, ресурсы и системные пакеты. Равенство номинальной API-версии не означает совместимость со старой ревизией. OS и Flare используют build-local generated paths; ручное обновление исходных снимков не заменяет генерацию.
